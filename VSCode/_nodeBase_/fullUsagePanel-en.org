** +
VS Code explained for someone who knows Emacs well: each VS Code concept mapped to its nearest
Emacs concept, and where the two differ. The one difference that explains most of the others:
Emacs derives a buffer's project from its file; VS Code puts every file into a window, and the
window has a declared folder. In Emacs the project belongs to the buffer; in VS Code, to the window.

Written 2026-11-02, while starting Blee + VS Code Claude from scratch (the bisos.aiActivity newStart
panel). The Blee layer over VS Code is blee/vscode-claude (=b:vscode=, =b:vscode:claude=).
** -B|

* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *VS Code Concepts Mapped to Emacs:* |]] <<Mapping>>   the table  [[elisp:(org-shifttab)][<)]] E|

| VS Code                   | Nearest Emacs                | Where they differ                   |
|---------------------------+------------------------------+-------------------------------------|
| Text document             | Buffer                       | The same idea                       |
| Editor (a tab)            | A window showing that buffer | The same                            |
| Editor group (a split)    | Splitting the frame          | The same                            |
| Side bar: Explorer        | dired, treemacs              | Only within the window's folder     |
| Side bar: Search          | rgrep, rg                    | Only within the window's folder     |
| Side bar: Source Control  | magit                        | Only the window's folder's repos    |
| Panel: Terminal, Problems | =*shell*=, =*compilation*=       | The terminal starts in the folder   |
| Command Palette           | M-x                          | The same                            |
| Settings, =.vscode/=        | custom.el, =.dir-locals.el=    | Per folder, not per directory tree  |
| Extension                 | Package                      | One extension host per window       |
| *Window*                    | *A frame --- or a whole Emacs* | See below                           |
| *Folder, workspace*         | *A project root (project.el)*  | Fixed by the window, not per buffer |
| =code= command              | emacsclient                  | VS Code picks the window            |

####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "The Window" :anchor "Window" :extraInfo "closer to a separate Emacs than to a frame"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *The Window:* |]] <<Window>>   closer to a separate Emacs than to a frame  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
An Emacs frame is one view into one Emacs: every frame shares every buffer, every package, every
process. A VS Code window is closer to a separately started Emacs: it has its own open files
(editors), its own extension host process running its own copy of every extension, its own
terminals, and its own Claude Code panel with its own sessions. A file open in one window is not
"a buffer" of another window.

The =code= command plays the role of emacsclient: it hands the request (a file, a folder, a URI) to
the running VS Code, which chooses the window that gets it. =--reuse-window= says the last active
window; =--new-window= a new one.
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "Folders and Workspaces" :anchor "Folder" :extraInfo "why VS Code wants a folder"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *Folders and Workspaces:* |]] <<Folder>>   why VS Code wants a folder  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
A window opened with a folder is a window *on* that folder: Explorer, Search, Source Control, the
folder's settings (=.vscode/settings.json=), its tasks and debug configurations, the terminal's
starting directory, and Workspace Trust are all scoped to it. A window with no folder (an "empty
window") is like Emacs with no project: a file can be edited, but those features have nothing to
work from.

A window can hold several folders, a /multi-root workspace/ (a =.code-workspace= file, or
=code --add=). For Blee + Claude we keep one folder per window.

Opening a folder in a window that already has one *replaces* it: the window reloads, and its Claude
sessions end (their transcripts stay and can be resumed). =--reuse-window= on a folder does that to
the last active window.
** -B|
####+BEGIN: blee:bxPanel:foldingSection :outLevel 1 :title "Claude Code in VS Code" :anchor "Claude" :extraInfo "the window's folder is the session's directory"
* [[elisp:(show-all)][(>]]  _[[elisp:(blee:menu-sel:outline:popupMenu)][±]]_  _[[elisp:(blee:menu-sel:navigation:popupMenu)][Ξ]]_       [[elisp:(outline-show-subtree+toggle)][| *Claude Code in VS Code:* |]] <<Claude>>   the window's folder is the session's directory  [[elisp:(org-shifttab)][<)]] E|
####+END
** +
A Claude Code session started in a VS Code window takes the window's folder as its working
directory, for the life of the session. That directory decides what the session loads: the
=CLAUDE.md= chain, =.claude/commands=, =.claude/skills=, project settings. So what a Claude session
knows at its start is decided by which folder its window was opened on --- not by which file is
being edited. A session in a window with no folder starts at no project root (where it does start
is still to be verified).

A Claude session's directory is therefore a property of the window, chosen when the window is
opened. In Emacs terms: as if =default-directory= were fixed per frame, at frame creation.
** -B|
