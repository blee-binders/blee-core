-p emacs= value it is about to launch. So the file is a DERIVED artifact, not state to be

*** 3.3.1) <<boot-blee>> at  [[/bisos/blee/env3/boot/boot-blee.el]]
**** We can get here from [[doom+blee]]  with *b:doom:enabled?* set to true.
**** We can get here from [[pure-blee]]  with *b:doom:enabled?* set to nil.
**** At this point straight has been bootstrapped. Either in Doom or in pure-blee.
**** Goal is to allow for all follow on modules to be in COMEEGA. As early as possible.
**** increase grabage collection limit for booting.
***** <<gcThresholdBug>> BUG FOUND AND FIXED <2026-09-07>. Read this before touching GC here.
boot-blee.el used to stash gc-cons-threshold at load time and re-impose that stashed value
on a 5-second idle timer. Under Doom that DISABLES GARBAGE COLLECTION for the session.
Doom's early-init.el sets gc-cons-threshold to most-positive-fixnum for the duration of
startup and restores it to 16MB at the end, with its own comment reading:
   "DON'T COPY THIS BLINDLY! If it's not reset later there will be stuttering, freezes,
    and crashes."
boot-blee.el loads WHILE that value is still most-positive-fixnum, so it stashed
most-positive-fixnum and then overwrote Doom's restored 16MB with it.
- Symptom: blee grows steadily slower and heavier the longer it runs, EVEN WHEN IDLE,
  because nothing is ever collected. Idle time arms it rather than helping.
- Confirmed on blee-31: =M-: gc-cons-threshold= => 2305843009213693951.
- Whether it bit depended on load order relative to Doom's restore, which is why it varied
  by doom version --- blee-28 felt fine while blee-31 did not, from identical blee code.
- Fix: boot high as before, but hand back a SANE value (16MB, matching Doom), never a
  captured one. See b:gc:sane-threshold in boot-blee.el.
- Diagnostic for the future: =M-: gc-cons-threshold= should read 16777216, not 2305843009213693951.

** *1. SHARED vs PER-VERSION --- the one to read first*
Every coexistence bug so far has lived in this distinction, and nothing else states it.
#+begin_example
                      emacs 30             emacs 31            emacs Next (32)
                      ────────             ────────            ───────────────
  doomFrameworkBase   doomemacs-30         doomemacs-31        doomemacs-32
  (doom source)       @ doomPin(30)        @ doomPin(31)       @ latest
                           │                    │                    │
                           ▼                    ▼                    ▼
  doomRunBase         emacsVers/30.2/      emacsVers/31.1.50/  emacsVers/32.x/
  (built tree)          doom-run-blee3       doom-run-blee3      doom-run-blee3
                           │                    │                    │
                           └──────────┬─────────┴────────────────────┘
                                      ▼
  doomDirBase                 dooms/doom-base-blee3          <-- (!) SHARED
  (config + packages)         init.el  packages.el  config.el
#+end_example
*** doomFrameworkBase :: per emacs MAJOR version. Was a single shared clone until
<2026-09-07>; that is why two emacs versions could not coexist.
*** doomRunBase :: per FULL emacs version (31.1.50, not 31). Derived from the binary.
*** doomDirBase :: *SHARED by every version and every build.*
**** Consequence 1: builds must be SERIALISED. vis_switchInitTo rewrites config.el at the
start (sansBlee) and end (withBlee) of every build. Two concurrent builds race on it.
**** Consequence 2: package pins are shared. There is nowhere to say "package X at version
A for emacs30, version B for emacs31".
** *2. SELECTOR -> DERIVATION CHAIN*
Kills the trap that =-p emacs=sys= yields 28.2 while =-p emacs=28= FAILS.
#+begin_example
  -p emacs={ sys | 0 | 28 | 31 }          <-- a SELECTOR, not a version
        │
        ▼   bleeLib.sh :: vis_getEmacsExec
   /usr/local/bin/emacs-31        or    $(which emacs)
   (fails if that file is absent)       (whatever sys emacs happens to be)
        │
        ▼   bleeLib.sh :: vis_getEmacsVerFromExec   <-- asks the BINARY
     "31.1.50"
        │
        ├── cut -d. -f1 ──▶ "31" ──▶ doomPinTable ──▶ doom commit
        │                        └─▶ doomFrameworkBase   (per MAJOR)
        │
        └────────────────────────▶ doomRunBase           (per FULL version)
#+end_example
*** RULE: always key on the DERIVED version, never on the selector.
*** Observed: on a node whose sys emacs is 28.2, =-p emacs=sys= -> 28.2 works, while
=-p emacs=28= FAILS, because /usr/local/bin/emacs-28 does not exist there.

Makes it obvious why a pinned doom still broke: the arrow INTO it came from a floating box.

       └─▶ dooms/doomemacs-31 @ pinned doom commit        [doomFrameworkBase]

       │   deleteRunBase  ──▶ rm -rf doomRunBase
       │   cp -r doomFrameworkBase/. ──▶ doomRunBase   (dotfiles included!)

       │   doom --force install    ── clones+builds ~198 pkgs into

  blee -p emacs=31 -i run doom-blee3
       └─▶ emacs-31 --with-profile doom-blee3
             consuming doomRunBase + DOOMDIR=doomDirBase

=(if noninteractive 27 29)= --- so a BUILD can succeed on an emacs that cannot RUN it.

** *The rule* :: pin what does not make releases with a TABLE; hardcode a TAG for what does.
*** doom makes NO releases -> doomPinTable in bleeLib.sh maps emacsMajor -> doom commit.
That table records a correlation we established by TESTING; it exists nowhere else.
*** emacs DOES make releases -> the tag is hardcoded in srcPkgSpecPrep_emacs<NN>_git in
lcaEmacsSrcBinsPrep.sh. No table --- "31.1" already denotes it, and the per-version function
IS the table entry. Add "branch" as srcObtainForm for the daily tip.
*** tree-sitter DOES make releases -> tag hardcoded (v0.27.0) in the same script.
** *STILL UNPINNED <2026-09-07> --- the known gap*
*** straight's RECIPE REPOSITORIES are a third upstream and are NOT pinned: melpa,
gnu-elpa-mirror, nongnu-elpa, el-get, emacsmirror-mirror --- plus straight.el itself.
*** They live in <doomRunBase>/.local/straight/repos/ ALONGSIDE ordinary packages, so straight
treats them as packages and they are pinnable by the same mechanism.

** +
** This describes CURRENT behaviour, verified <2026-09-06 Sun>. Not a plan.
** Question it answers: if blee is built for both emacs28 and emacs31, does launching one
break the other? *No --- not when launched through blee.*
** *What is per-version on disk (nothing is shared, nothing is lost)*
*** doomRunBase   :: /bisos/blee/emacsVers/<emacsVer>/doom-run-<profile> --- per emacs version
*** doomFrameworkBase :: /bisos/blee/dooms/doomemacs-<emacsMajor> --- per emacs MAJOR version
since <2026-09-06>. Before that a single shared clone was git-reset per build, which could
NOT support two versions. See doomProfilePrep in bleeLib.sh.
*** Building for one emacs version never touches another's trees.
** *Why launching still works --- the profiles file is derived, not state*
*** vis_run in the blee script does, in this order:
    emacsExec=$(vis_getEmacsExec ${emacs}) ; G_forceMode=force ; vis_emacsProfilesUpdate ;
    ${emacsExec} --with-profile <profile> &
*** That REGENERATES ~/.emacs-profiles.el on every run, from the same -p emacs= value it is
about to launch. So the file always describes the emacs being started.
*** blee -p emacs=28 -i run doom-blee3  -> profiles rewritten to 28.2   -> emacs-28  -> matched
*** blee -p emacs=31 -i run doom-blee3  -> profiles rewritten to 31.1.50 -> emacs-31 -> matched
*** Switching back and forth is free. There is no migration and no state to preserve.
** *Where it DOES break --- bypassing blee -i run*
*** ~/.emacs-profiles.el is a single global file reflecting whichever version ran LAST.
Anything that launches emacs without going through blee -i run reads a possibly stale file:
**** bare =emacs --with-profile doom-blee3= (bleeDoomsManage.sh's own examples suggest this)
**** desktop launchers, .desktop entries, a new emacsclient daemon
*** This is a live hazard as soon as more than one emacs version is built --- it is NOT
introduced by, and not specific to, the chemacs retirement.
** *The failure is loud, not silent*
*** doomemacs lisp/doom.el does, near the top:
    (let ((old-version (eval-when-compile emacs-version)))
      (unless (equal emacs-version old-version) (user-error "Doom was compiled with Emacs %s,
      but was loaded with %s. Run 'doom sync' to recompile it.")))
*** It is exact string equality on the FULL version, so 28.2 vs 31.1.50 refuses to start with
a clear message. You get an error, not corruption.
*** NOTE, tested and NOT the mechanism: raw byte-code is not the barrier. emacs 28.2 loaded an
emacs-31-compiled .elc without complaint in a direct test. Doom's explicit guard is what stops
it. (Native-comp .eln IS version-keyed --- /usr/local/lib/emacs/<ver>/native-lisp/<ver>-<hash>/
--- but doom's error fires first.)
** *If the bare-emacs path needs hardening*
*** Option 1: version-suffixed profile names (doom-blee3-28, doom-blee3-31) so entries for all
built versions are present simultaneously. Needs a change to vis_emacsProfilesStdout in blee.
*** Option 2: [[chemacs-obsolescence]] --- --init-directory removes the shared global file from
the picture entirely, which is the cleaner fix. Gated on dropping emacs-28.
*** Neither is needed for blee -i run to work with several versions today.

** *STATUS <2026-09-06 Sun> :: DOCUMENTED, NOT DONE.* Nothing here has been acted on.
Recorded so the reasoning survives to whenever emacs-28 is finally dropped. The gating

** *What --init-directory gives us*
*** Emacs *29* added =--init-directory=DIR= (etc/NEWS.29). Note: 29, not 30.
*** It sets =user-emacs-directory=, which is the one thing we actually use chemacs for.
*** VERIFIED <2026-09-06 Sun> on 31.1.50: =--init-directory= takes effect BEFORE early-init.el
is read. A probe profile logged user-emacs-directory already pointing at the profile dir
from inside early-init.el. This is the load-bearing detail --- chemacs-load-user-early-init
exists precisely to arrange that ordering, so if the option did not do it, the option
would be useless to us.
*** Present in 29, 30, 31.1.50. *ABSENT in 28.2* --- confirmed via =emacs --help=.
** *What chemacs does that --init-directory does not*
Chemacs profiles in ~/.emacs-profiles.el carry six keys. --init-directory replaces one.
*** user-emacs-directory :: REPLACED by --init-directory
*** env :: NOT replaced. This is how every doom profile of ours sets DOOMDIR.
*** server-name :: NOT replaced
*** custom-file :: NOT replaced
*** straight-p :: NOT replaced
*** nix-elisp-bundle :: NOT replaced
** *Why that gap is small for us specifically*
*** Of the six, only =env= / DOOMDIR is actually used by our profiles.
*** We already launch through a shell script --- /bisos/blee/bin/blee. A shell script exports
DOOMDIR in one line. chemacs mainly serves people who run bare =emacs= with no wrapper.
We do not.
*** Doom honors EMACSDIR natively (doomemacs/bin/doom sets it; doom.el's documented load
sequence is written in terms of $EMACSDIR), so doom never needed chemacs either.
*** ~/.emacs-profiles.el is not merely generated --- it is REGENERATED on every =blee -i run=
(see [[multi-emacs-coexistence]]). It is a derived artifact with no durable state in it, so
retiring it costs nothing and migrates nothing. The profile-naming layer is already ours.
chemacs is a redundant indirection sitting between two things we control.
** *The blocker --- the gating condition*
*** emacs-28 has no --init-directory. blee still supports emacs28 via bleeLib.sh::vis_getEmacsExec,
and sys emacs on some nodes IS 28.2 (it is what the existing emacsVers/28.2 tree came from).
*** So this is NOT a swap. Before emacs-28 is dropped it would mean carrying BOTH paths ---
chemacs for <=28 and --init-directory for >=29 --- which is worse than either alone.
*** Second order: ~/.emacs.d is a chemacs checkout and is currently the only reason a bare
=emacs= launched outside the blee script works at all. Removing chemacs changes behaviour
for anyone not going through blee. Decide deliberately what bare =emacs= should then do.
*** But note the bare-emacs path is ALREADY unreliable once more than one emacs version is
built, because ~/.emacs-profiles.el reflects whichever version ran last --- see
[[multi-emacs-coexistence]]. Retiring chemacs does not create that exposure; it removes it,
by passing the directory per invocation instead of via a shared global file. Treat this as an
argument FOR the migration, not against it.
** *Migration sketch, for when emacs-28 is dropped*
*** blee invokes: =emacs-<N> --init-directory=${doomRunBase}= with DOOMDIR=${doomDirBase}
exported by the script, instead of via the chemacs =env= key.
*** pure-blee (profile blee3) becomes =--init-directory=/bisos/blee/env3/boot=.
*** ~/.emacs-profiles.el and its generator (=blee -i emacsProfilesStdout= / =emacsProfilesUpdate=)
become unnecessary. Profile names live in blee alone --- =blee -i run doom-blee3= already IS
the interface.
*** ~/.emacs.d/{chemacs.el,early-init.el,init.el} can then go.
*** Sequencing note: doing this at the same time as an emacs version bump would confuse two
variables. Bump first, confirm, then migrate.
